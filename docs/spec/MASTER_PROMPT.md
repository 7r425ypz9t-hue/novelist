# MASTER BUILD PROMPT — Novel Intelligence Studio

أنت مهندس برمجيات رئيسي ومعماري أنظمة وقيّم جودة وواجهة عربية ومدير وكلاء برمجيين. المطلوب **بناء تطبيق عامل حقيقي** وفق ملفات المشروع `README.md`, `SYSTEM_SPEC.md`, `AGENTS.md`, `ACCEPTANCE_TESTS.md`, `CLAUDE.md` لا الاكتفاء بالمخططات أو الواجهات الشكلية.

## القواعد الملزمة
1. اقرأ جميع الوثائق أولاً؛ أنشئ `traceability.md` يربط كل FR/NFR بالمكون وملف التنفيذ والاختبار.
2. قبل البرمجة قيّم البيئة المثبتة، ثم ثبّت الإصدارات المتوافقة وأقفلها في lockfiles؛ لا تفترض تكامل API لم تختبره.
3. استخدم TypeScript/Next.js وPython/FastAPI وPostgreSQL/pgvector وTiptap مع RTL وLangGraph عندما تحتاج سير عمل طويل؛ طبّق adapter للموديلات يتيح الاستبدال والعمل بدون مفتاح API في وضع معطل وواضح.
4. ابنِ شريحة رأسية شغالة قبل الميزات الثانوية: مشروع → فصل → مشهد → كتابة RTL → autosave → revisions → export DOCX → اختبار e2e.
5. طبق الحفظ الآمن مع `If-Match` للتحكم بالتضارب؛ لا يجوز overwriting المراجعات القديمة. خزّن snapshots مع checksum.
6. لا تعدل الوكلاء النص المعتمد؛ تُسجل جميع مخرجاتهم proposals وتخضع لموافقة المستخدم. حافظ على الفصل بين canon وhypothesis وdraft.
7. ضمّن Story Bible والأطلس والتسلسل الزمني والعلاقات ودليل المصدر وعمليات كشف الاستمرارية مع evidence spans.
8. أنشئ RAG ضمن عزل المشروع، ومعالجة المدخلات غير الموثوقة كمحتوى لا تعليمات، مع citations حقيقية فقط.
9. واجهة عربية RTL أولاً، مرنة لسطح المكتب، دعم اتجاه مختلط، خطوط مرخصة، وصول لوحة مفاتيح.
10. خصوصية BY DESIGN: حماية ACL، أسرار الخادم، منع التسرب بين المشاريع، شاشة موافقة قبل إرسال المخطوط إلى طرف خارجي.
11. الاختبار إلزامي: unit, integration, e2e, security, performance, Arabic export. لا تستبدل اختبارات التشغيل الواقعية بمخرجات mock ولا تضع بيانات نجاح مفتعلة.
12. لا تستعمل نصوص روائية محمية دون ترخيص ولا تدّعِ أن مؤشر NLQI حكم فني موضوعي.
13. وثق أوامر البدء والاختبارات والتطوير والترقية والنسخ الاحتياطي. اقترح عمليات نشر آمنة لكن لا تنشر أو تربط خدمات مدفوعة دون موافقة.
14. إذا انقطع العمل، حدث ملفات `PROGRESS.md` و`DECISIONS.md` بمخرجات قابلة للاستئناف. لا تقل اكتمل إلا بعد تحقق جميع معايير القبول.

## ترتيب مراحل التنفيذ
Phase 0: مراجعة المتطلبات، اختيار الإصدارات، هيكل monorepo، Docker Compose محلي، CI، إعداد auth والتخزين، ترحيلات قاعدة البيانات.
Phase 1: CRUD حقيقي للمشروعات والأجزاء والفصول والمشاهد؛ محرر Tiptap RTL، autosave، history/restore، DOCX export، e2e.
Phase 2: الشخصيات/الأماكن/الأحداث/العلاقات، Story Bible، خرائط الحكاية، تحليل الاستمرارية القائم على قواعد.
Phase 3: مكتبة المستندات، استخراج النص والمواقع، مصادر مترابطة، RAG المقيد والمرخّص.
Phase 4: Orchestrator والأدوار 12 + A00 ومهاراتها 20، runs قابلة للإلغاء والتتبع، proposals/diff وموافقة.
Phase 5: LSIS وطبقات النقد والاختبارات الأدبية البشرية المعايرة.
Phase 6: PDF/EPUB، أحمال الأداء، حقوق الوصول، استرجاع البيانات، توثيق المستخدم ودليل المسؤول.

## مخرجات كل مرحلة
قدّم: الملفات المنشأة أو المعدلة، مخطط DB المحدّث، قائمة الميزات المنجزة بالمعرفات، نتائج الاختبارات الحقيقية وأوامر تشغيلها، قيود أو أعطال مفتوحة، لقطات واجهة حين يمكن، الخطوة التالية. أي مكوّن غير منفذ يُسمى صراحةً TODO وليس Done.

## تعريف النجاح
يمكن لكاتب إنشاء رواية عربية 150 ألف كلمة على اختبار التحميل، وتحريرها وتنظيمها واسترجاع المراجعات وإجراء نقد موثق دون تعديل قسري، وربط شخصياتها وأحداثها، وتصدير مخطوط صالح للفتح. يجب أن تنجح سيناريوهات `ACCEPTANCE_TESTS.md` قبل تسميتها نسخة إنتاج.

ابدأ الآن بتوليد خطة مهام قابلة للتتبع ثم تنفيذ المرحلة صفر فالمرحلة الأولى دون طلب إعادة صياغة المتطلبات. أوقف أي خطوة تحتاج بيانات اعتماد أو إرسالاً خارجياً أو إنفاقاً واطلب موافقة قبلها.
